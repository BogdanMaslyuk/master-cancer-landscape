# Инструкции для Codex — Master Cancer Landscape (MCL)

## Контекст
MCL — исследовательская система сопоставления генов, белковых мишеней, опухолевых и клеточных моделей и экспериментальных данных о лигандах. Отвечай пользователю и оформляй научные отчёты **на русском**, сокращения расшифровывай при первом употреблении. Научные данные не заменяй модельными оценками.

Перед изменениями в TLS V3 прочитай `docs/research/MCL_CODEX_HANDOFF_2026-11-23_RU.md` и методику нужного этапа. В проекте есть отдельные черновые PR #13–16, не слитые в основную ветку.

## Обязательные правила
- **Никакого автоматического объединения веток/PR.** Только отдельная ветка или изолированная рабочая копия, изменения и результаты на проверку.
- **Без изменения научного эталона:** 65 PYZ, 13 исходных мишеней, матрица 845 пар, исходные DepMap/UniProt/ChEMBL/BindingDB снимки, `data/raw/`, `data/processed/`, `data/runtime/` — только чтение, пока пользователь прямо не одобрит конкретное изменение.
- Не удалять файлы, архивы, базы, рабочие копии; не переименовывать большие научные источники и не очищать кэш без согласования.
- Все отчёты и временные диагностические результаты создавать **вне научных каталогов**, отдельно от исходных данных. Учитывать Git LFS, размеры файлов и лицензии; не отправлять локальные большие базы и персональные данные в GitHub.
- По умолчанию сеть выключена; публичные источники — только разрешённые, с зафиксированным релизом, контрольной суммой и происхождением. Большие загрузки, изменение разрешений или установка системного ПО — только с согласия пользователя.
- Различать: сопоставление HGNC ↔ UniProt; измеренные Ki/Kd/IC50 у **известных** веществ; предсказание взаимодействия PYZ; генетическая зависимость CRISPR; цитотоксичность. Нельзя выдавать одно за другое.
- Отсутствие измерения в неполном локальном снимке — `NOT_ASSESSED`, а не отрицательный результат. Не путать IC50 в клеточном тесте с константой связывания. Не объединять измерения ChEMBL/BindingDB без проверки дублирования.
- При сомнении в идентичности белка, нескольких цепях, изоформах, цензурированных показателях или изменении схемы исходника — `REVIEW_REQUIRED`, не скрывать неопределённость.
- Не утверждать `scientific_acceptance=APPROVED` и `merge_permitted=true` без явной научной приёмки.

## Рабочий процесс
1. Прочитай текущее ТЗ и покажи краткий план и проверяемые критерии успеха.
2. Выполни ревизию `git status`, ветки, версий инструментов и доступных локальных источников; сохрани неизменность данных.
3. Перед правками создай отдельную ветку/рабочую копию; не работай напрямую на `main` или рабочей научной папке.
4. Делай минимальные проверяемые изменения, синтетические тесты + анализ реальных данных только при наличии проверенных исходников.
5. Приводи точные команды и итоги тестирования, ссылки на изменённые файлы, SHA/версию источников, ошибки и научные ограничения. Не называй успешные тесты доказательством научной корректности.
